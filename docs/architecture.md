# Architecture

The active v0.8 continuation repairs report delivery and carry-forward without expanding physics. New provenance and rendering contracts are explicitly versioned; historical codecs, identities and issued bytes remain supported. Capacity forecasts distinguish actual retained inventory from estimates and final admission. Optional SKP intake requires source/license review, bounded native execution and independently known compatibility fixtures before exposure; the existing inert GLB path remains. See v0.8 specification (`docs/v0.8-spec.md` in source) and acceptance (`docs/v0.8-acceptance.md` in source).

The active v0.7 continuation adds immutable reviewed scope revisions and report issues around existing shared services. Exact selected run/reference snapshots, reviewed carry-forward and versioned aligned figures remain derived evidence; they never change simulation identities or historical bytes. Active viewport selection and historical mapping inspection use separate controlled identities. Bounded cancellation-aware verified metadata reuse still rechecks actual bytes. See [v0.7 specification](v0.7-spec.md) and [implementation plan](v0.7-implementation-plan.md); concrete contracts and verified acceptance follow implementation.

The v0.6 continuation adds a separate bounded architectural-reference layer around the existing workbench. It does not expand the thermal geometry or qualify historical daylight/energy methods. See [reference contracts](v0.6-reference-contracts.md) and the [acceptance ledger](v0.6-acceptance.md). The earlier phase descriptions below remain historical architecture records.

The active v0.5 extension adds a professional thermal workbench around the existing v0.4 thermal model, native EnergyPlus adapter and shared report services. Its [contracts](v0.5-contracts.md) are additive, and its [acceptance ledger](v0.5-acceptance.md) does not inherit installed acceptance from v0.4. The retained v0.3 extension provides versioned static/hour/annual daylight studies, local EPW data, separate physical/metric identities and bounded chunked results; its scientific qualification remains failed and its finite investigation is stopped. Legacy model/run codecs and engine identities remain separately dispatched without rewriting old evidence. Frontend requests bounded result slices and Rust-derived metrics rather than full matrices or local physics.

The Rust core defines versioned inputs, authoritative geometry, sensor generation, scientific conversion, hashes, statistics and compatibility. The Radiance adapter produces bounded engine inputs and invokes the pinned executables. The runner/application service coordinates one job, process supervision, persistence, comparison, evidence export and replay. CLI and Tauri commands call the same service; React/Three.js only renders validated geometry/results and issues typed bounded requests.

Simulation adapters produce evidence. Data providers supply validated inputs with source rights. Assessment modules can consume evidence but do not define simulation physics. Only the Radiance adapter and synthetic input data exist in v0.1; the latter two categories are architectural boundaries, not a marketplace or dynamic ABI.

Durable project data is relative, JSON/text and checksummed. Active jobs and octrees live in per-user local cache. Finalization validates before promotion and manifest update. Historical runs preserve their input snapshots; current inputs determine staleness. Packages never supply executable commands. Native cancellation/shutdown supervises the entire process tree.

## v0.2 document and workspace boundaries

`workspace/useDocument.ts` coordinates the native application service, pending evidence, project revisions and destructive-action protection. `DocumentHistory` stores complete before/after input snapshots only after a successful Rust validation. Commands, Properties and viewport handles call that same accepted-edit path. A provisional drag lives inside the viewport until commit; Escape drops it. Failed validation cannot advance either history stack. Save updates the persistence baseline without resetting history; another document or explicit disk reconciliation resets it.

`ViewportEngine` owns one WebGL renderer and four persistent camera objects for the lifetime of `SceneView`. Its scientific-to-renderer transform is explicit. Validated input changes replace affected rendered geometry resources; selection, colors and layers update display state. Framing happens on new-document initialization or an explicit navigation command. Selection uses semantic IDs, not triangle IDs. Preview/snapping math is interaction geometry; Rust remains authoritative for final validation, geometry, hashes and saved simulation inputs.

Scientific document, viewport display, selection and simulation state are separate. The optional `greenlens.display.v0.2` extension contains cameras, layers, object display overrides and modeling aids. It is excluded from scientific hashes/history. The base project schema remains 0.1.0 so v0.2 reads existing v0.1 projects; older applications may reject a project after display state has been added. Immutable run schemas and bytes remain untouched. See [persistence](persistence.md) for revision conflicts, full-copy promotion and bounded export.

Build provenance is generated by Cargo from the actual checkout at build time, with explicit verifiable CI assertions. See [build provenance](build-provenance.md). No source identity is cached in the development shell.

## v0.3 application services

`greenlens-core::weather` validates the original EPW and produces a versioned normalized input/time axis. `greenlens-core::study` owns study validation, physical/metric identity and streaming weighted metric arithmetic. The provider has no engine dependency. `greenlens-radiance::annual` owns recognized versioned transport recipes, finite solar-disc visibility and monitored subprocesses; selected-hour and annual modes share that implementation. Historical methods retain their own exact profiles and generated process sequences. The provisional paired-primary method streams a versioned, bounded generator through the Windows Job supervisor. Its portable receipts and resource records are platform-neutral; no process runs during historical inspection. The scaled coefficient receiver remains separate from the unit receiver used for direct transmission.

The runner's `weather`, `studies`, `climate`, `timeseries` and `climate_export` modules expose portable import, study transactions, immutable evidence, bounded queries and recognized replay. `climate_job` uses the same one-active-job supervisor, cancellation, pending-evidence protection and manifest promotion as static runs. Expensive Tauri operations run on blocking workers so result loading does not block the UI event loop. One hourly vector or one sensor series crosses IPC; complete matrices remain in bounded files.

The runner's `qualification` module interprets immutable climate evidence through a compiled, versioned registry. It separates retained process completion, the actual integrity-check scope, current physical/metric relationships and exact-method scientific qualification. The registry binds full numerical and engine identities and the recognized recipe contract; unknown combinations are unassessed. Failed profile-level acceptance is not a claim that every value is wrong. Limited positive assessments require an explicit tested input scope. CLI, desktop and export use the same service; imported assessments never control execution or override the compiled registry. A supplementary export assessment does not change embedded run bytes or scientific hashes.

Document history distinguishes model transactions from study transactions. Rust validates both. Undo restores only the edited alternative's model/study, retaining runs and weather added later. Restoring an initially absent legacy climate extension removes it only if no later climate evidence or other study requires it. Saving does not clear history. Physical-result lookup selects the newest compatible immutable snapshot; changed metric settings request newly identified derived values rather than changing that snapshot.

## v0.4 energy and reporting foundation

The [energy specification](v0.4-energy-spec.md) adds a separate versioned thermal document and energy study without changing old daylight identities. Rust owns zones, thermal surfaces/adjacency, constructions, gains/schedules, systems, validation and comparison. The EnergyPlus adapter generates pinned epJSON and extracts bounded native CSV/JSON through the existing job supervisor. A distinct weather suitability profile validates the fields consumed by thermal simulation; daylight weather acceptance is insufficient. No application database, Python or OpenStudio runtime is required.

The shared runner/CLI/Tauri services produce one versioned energy report dataset from immutable run evidence and explicit derived inputs. HTML, owned Typst PDF templates, CSV/JSON and chart/model SVG/PNG assets consume it. PDF generation is offline and headless through a pinned audited renderer; imported packages never supply executable templates. Physical inputs, meter processing, carbon factors and presentation retain separate identities. In particular, operating schedules affect energy physics and cannot be treated as daylight-style metric-only edits.

Energy engine qualification remains independent of daylight qualification, execution success, integrity and currentness. The supplementary registry binds complete method and physical input identities; historical evidence stays immutable and unknown combinations remain unassessed. Native engine/resource, license and exact synthetic numerical evidence are linked from the energy status. The [installed verification record](v0.4-native-verification.md) distinguishes those headless checks from the still-unverified desktop workflow. Later regional baseline/rule modules consume suitable evidence through a separate boundary.

## v0.5 authoring, investigation and presentation

Core thermal transactions produce a complete preview with affected semantic IDs, validation issues and candidate identity. Shared runner commit services recompute against current inputs/locks and update explicit A/B targets atomically. Accepted design history contains model/study snapshots; copied designs transfer no evidence or report metadata. Rust generates all pickable thermal polygons, while Three.js owns only display transforms, four cameras, selection and navigation. Hidden objects remain scientific inputs. Local display and draft recovery stores have explicit bounds and never establish accepted scientific identity.

The frontend document controller retains incomplete structured/raw text and guards save, calculation and replacement with Apply/Discard/Cancel. Async Apply accepts only the captured draft; later text is not discarded by an older response. Typed comparisons supplement the historical comparison codec, distinguishing fan efficiency/pressure design changes from airflow/schedule service changes. Core, adapter, retained-weather and dependency preflight expose their separate check scopes rather than a generic accuracy label.

`energy_navigation` streams bounded requested or searched chunks for exact local-standard date/day/range/peak/unmet investigation. Five-minute energies align to common ten-minute demand in Rust; comparison compatibility remains strict. The catalog reads bounded checked metadata and labels that narrower integrity scope. The sensitivity planner fixes exact inputs/methods and deterministic reuse before the finite workflow reserves and starts one missing case through the existing Application job owner. Portable plan/event sidecars retain failure/cancellation and are checked on open/copy/export. A successful numerical assessment cannot update the scientific registry.

The v0.5 report supplement binds the unchanged immutable base dataset to issue metadata, new typed service differences, selected attachments and owned templates. All rendered products share Rust values; imported package assessments/templates have no execution authority. The dry-envelope weather admission also has its own recognized method/recipe; it never changes strict historical admission. The [real-weather applicability protocol](v0.5-real-weather-protocol.md) is blocked before annual execution because complete curve-call input coverage has not been established. [Launch and delivery](v0.5-delivery.md) distinguishes implemented paths from pending exact-source/native acceptance.

## v0.6 reference intake and verified project opening

`project_open` separates cheap unverified manifest admission from one guarded, cancellable evidence operation. A private operation-local provider reuses only records that have passed the real series reader and arithmetic checks. Sensitivity inspection uses those exact records, not a second open. The final acceptance fence rehashes actual observed content and checks the manifest revision; no timestamp-only cache is trusted. The receipt states its as-of-open integrity scope and does not promise future immutability or scientific qualification. Progress and cancellation use bounded I/O/row checkpoints. The frontend accepts the candidate atomically and suppresses cancelled/late responses while preserving the previous document and pending completed jobs.

`greenlens-core::reference` admits a bounded static GLB subset, composes transforms in double precision and emits sealed normalized chunks plus a versioned receipt. Original files remain external by explicit policy. `runner::reference` owns import, revision conflicts, copied assets, exact-vertex measurement and scope transactions. Reference appearance never supplies thermal properties. Source occurrences are distinct revision-bound identities, not editable thermal solids. The renderer uses compact local-origin buffers for display while measurements, bounds and accepted transforms remain Rust-owned.

`architectural_scope` binds explicit mappings, assumptions, source measurements and scope to admitted reference and analytical input identities. Editing scope is derived history; undo retains subsequently collected evidence and reference revisions. Reimport does not silently rebind mappings. The architectural report supplement evaluates the selected immutable energy snapshots and generates deterministic owned vector figures from admitted geometry. All normalized assets accompany a v0.6 portable energy package; original proprietary sources/conversion files are explicitly excluded. Old report datasets and replay identities remain separately dispatched and unchanged.
