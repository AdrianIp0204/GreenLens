# Portable evidence and OneDrive

Projects contain a manifest and immutable run directories. Finalized runs carry their compact inputs, output, provenance and checksums; disposable octrees and active calculations stay in the configured local application cache. Run promotion copies validated files into a new temporary directory within the project, verifies the copied checksums, promotes that directory, and only then allows the manifest to reference it. Individual destination files are created exclusively. An existing run identifier must already contain the same evidence.

The writer holds an exclusive lock and detects manifest revision conflicts before replacement. On Windows it also retains directory handles that deny renaming or deletion of the project and destination run directory during promotion. Existing destination junctions, symbolic links and other name-surrogate reparse points are rejected, including a project root supplied through a junction. Cross-device simultaneous editing remains unsupported.

OneDrive marks ordinary cloud-managed files with reparse metadata too. GreenLens inspects the actual Windows reparse tag through a handle opened without following a reparse target. Known OneDrive/cloud tags are accepted when the requested evidence file is fully available locally. Offline or partially recalled files produce an actionable error: make the project available offline in OneDrive, then retry. A cloud directory may contain unrelated online-only files; each requested evidence file is checked individually. Unknown reparse implementations are rejected rather than presumed safe. This is a bounded file-integrity precaution, not a sandbox against a malicious local process with the same account privileges.

The distinction follows Microsoft's [reparse tag definitions](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-point-tags), [file attribute definitions](https://learn.microsoft.com/en-us/windows/win32/fileio/file-attribute-constants), and [FileAttributeTagInfo handle query](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_attribute_tag_info). Native tests create actual Windows junctions for redirected project, `runs`, and existing-run destinations. Attribute-classification tests cover hydrated cloud variants and unavailable files; those synthetic attributes do not establish that a particular cloud provider or hydration configuration has been exercised.

Source remains in the chosen checkout. `.gitignore` excludes build products from Git, but does not disable OneDrive synchronization of `node_modules` or any other directory. Build output and simulation scratch use `%LOCALAPPDATA%/GreenLens` as documented in the installation guide.
