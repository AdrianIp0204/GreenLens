# Portable evidence and OneDrive

Projects contain a manifest and immutable run directories. Finalized runs carry their compact inputs, output, provenance and checksums; disposable octrees and active calculations stay in the configured local application cache. Run promotion copies validated files into a new temporary directory within the project, verifies the copied checksums, promotes that directory, and only then allows the manifest to reference it. Individual destination files are created exclusively. An existing run identifier must already contain the same evidence.

The writer holds an exclusive lock and detects manifest revision conflicts before replacement. On Windows it also retains directory handles that deny renaming or deletion of the project and destination run directory during promotion. Existing destination junctions, symbolic links and other name-surrogate reparse points are rejected, including a project root supplied through a junction. Cross-device simultaneous editing remains unsupported.

OneDrive marks ordinary cloud-managed files with reparse metadata too. GreenLens inspects the actual Windows reparse tag through a handle opened without following a reparse target. Known OneDrive/cloud tags are accepted when the requested evidence file is fully available locally. Offline or partially recalled files produce an actionable error: make the project available offline in OneDrive, then retry. A cloud directory may contain unrelated online-only files; each requested evidence file is checked individually. Unknown reparse implementations are rejected rather than presumed safe. This is a bounded file-integrity precaution, not a sandbox against a malicious local process with the same account privileges.

The distinction follows Microsoft's [reparse tag definitions](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-point-tags), [file attribute definitions](https://learn.microsoft.com/en-us/windows/win32/fileio/file-attribute-constants), and [FileAttributeTagInfo handle query](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_attribute_tag_info). Native tests create actual Windows junctions for redirected project, `runs`, and existing-run destinations. Attribute-classification tests cover hydrated cloud variants and unavailable files; those synthetic attributes do not establish that a particular cloud provider or hydration configuration has been exercised.

Source remains in the chosen checkout. `.gitignore` excludes build products from Git, but does not disable OneDrive synchronization of `node_modules` or any other directory. Build output and simulation scratch use `%LOCALAPPDATA%/GreenLens` as documented in the installation guide.

## v0.2 document recovery and complete copies

A completed job retains its immutable evidence until collection, complete-copy Save As, or an explicit discard succeeds. Starting another job or closing without a decision cannot silently replace pending evidence. If another writer changes the project manifest during a calculation, ordinary collection reports the revision conflict. Explicit reload/reconcile reloads the current disk models and appends the completed historical snapshot; it does not merge or overwrite local unsaved model edits. The desktop must explain that those local edits are replaced before reconciliation. Results whose original inputs differ from the reloaded design remain historical/stale.

Save As creates a complete portable project in a new or empty destination. It preserves current unsaved models, every referenced historical run, and pending completed evidence by default. Because it does not modify the source manifest, recovery copying is allowed after a source revision change. The source project identity, every immutable run's checksums and the pending job's project binding are still checked. The new manifest is published only after all referenced evidence has been copied and validated; a failed copy never advertises incomplete evidence as a completed project. An existing nonempty destination is rejected. Save As does not depend on the original scratch directory after success.

The v0.2 reader accepts unextended v0.1 manifests and adds the optional `display_state` field described by `schemas/project-v0.2.schema.json` and `schemas/display-v0.2.schema.json`. The project and scientific `schema_version` remain `0.1.0`; presentation state carries its own `greenlens.display.v0.2` identifier. Old strict v0.1 readers may reject the new optional field. Immutable run files are copied without rewriting their schema, input or provenance. Camera coordinates use world ENU. Cameras, colors, visibility, edit locks and construction aids never enter scientific input hashes or generated Radiance geometry.

## Bounded evidence archives

Archive creation and extraction share limits of 5,000 files, 64 MiB per uncompressed file and 256 MiB total uncompressed content, including the generated report, comparisons and checksums. Relative entry names are at most 240 bytes and unique without regard to ASCII case. The exporter preflights the referenced evidence before loading it, bounds generated files, then checks every final file before creating the output ZIP. Source files changing during the final copy cause failure. The reader independently enforces both declared and actual extracted byte counts. Rejections explain that the current project is retained and a smaller analysis project is needed.

Every historical run remains in the export. The report includes only the most recently saved A/B pair within each compatible comparison-condition group, instead of every historical A-by-B combination. This bounds comparison growth while preserving the underlying evidence for explicit pair selection through the CLI.
