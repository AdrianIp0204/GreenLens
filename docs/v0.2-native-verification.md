# GreenLens v0.2 native verification procedure

This is the reproducible acceptance procedure for the new workspace. No v0.2 installed workflow has been verified yet. Historical v0.1 observations remain in `native-verification.md` and are not fresh v0.2 evidence. Update each row only after its observed checks pass, recording failures and repairs without overwriting earlier evidence.

## Artifact and environment record

Use the per-user NSIS installation and embedded assets, without a development server. Record source commit and dirty identity, application/schema/adapter/engine versions, installer/CLI/installed-desktop SHA-256, unsigned status, Windows/WebView2 versions, prerequisite imports, and retained-notice checks. Build identity regression is described in `build-provenance.md`.

Create a fresh synthetic verification directory under `%LOCALAPPDATA%\GreenLens\native-verification\v0.2-<UTC timestamp>`. Keep native screenshots, screen/window measurements, process snapshots and exact local paths there; publish sanitized observations only. Include spaces and non-ASCII characters in portable project locations. Do not modify historical v0.1 runs or the originals used for compatibility tests.

Stage a previously verified synthetic v0.1 A/B project using `./scripts/prepare-native-verification.ps1 -V01Project <saved-project-directory>`. The script requires original v0.1 run provenance, checks contained run references, rejects linked content, copies to a new Unicode/spaces path, and verifies every copied and original file hash. It records `v0.1-fixture-hashes.json` and a separate private `local-paths.json`; only the copy may be changed or moved during compatibility tests.

Record actual display resolution, native window/client dimensions and Windows/WebView device scale. Test the 1366×768 and 1920×1080 layout targets with Properties, Layers and Analysis open/collapsed, command history expanded, and the table/log views accessible. If the physical display or available window area differs, retain exact measurements and state the difference. WebView zoom or emulated scaling, if used, is supplementary and must not be described as a different Windows DPI setting. Avoid changing global display settings merely to create a screenshot.

## Supporting checks and coverage limits

Native dialog tests cover Open, Save As and Export cancellation as well as successful path selection; ordinary operation must not require typed absolute paths. Commands, menu actions, shortcuts, Properties and handles must reach the same accepted-document transaction path. Record safe Enter-repeat behavior, command cancellation, autocomplete/prompts and text-field shortcut isolation. Test unsaved-new and already-saved documents separately.

Camera persistence, projected selection boundaries, snapping and one-transaction history also require meaningful automated interaction tests. Browser tests and synthetic fixtures are supplementary; they cannot be counted as real engine or installed Windows evidence. The current Windows automation API supplies left drag, clicks and wheel input but no documented held-modifier/right-button drag primitive. If that prevents a native navigation demonstration, record the exact coverage gap and seek an authorized manual observation rather than inventing a successful gesture.

The workspace's keyboard navigation is a hardware-independent supplement: focus a viewport, use arrow keys to navigate, Shift+arrows to pan Perspective, and plus/minus to zoom. Orthographic arrows pan without changing projection. Capture camera labels before/after and after mode, selection, input and layout changes. This demonstrates native camera persistence but is not evidence that an unperformed right-button drag occurred. A completed `sky.drag` cannot be interrupted mid-stroke; Escape rollback can be demonstrated with the application's provisional numeric transaction and supplemented by pointer-lifecycle regression.

The documented native automation API has no direct window-bounds setter. Use observed title-bar maximize/restore and a fresh-screenshot window-border drag, then read the app's Diagnostics values for actual client dimensions/DPR. Do not assume drag distance equals physical window size. Report screenshots with the measured dimensions. Do not replace a missing native sizing/scaling observation with CSS screenshots labeled as native. Use accessible diagnostics and saved display state to compare cameras; no injected app JavaScript or hidden test backend is required.

Run the unchanged scientific A–F suite, relevant Rust lifecycle/persistence tests, frontend checks/tests/build, CLI save/export/replay and Windows CI against the final implementation. Inspect newly added dependencies and refresh strict retained notices after lockfiles settle. A successful export must satisfy the shared reader bounds; exercise that using synthetic boundary fixtures, not hundreds of expensive simulations.

Completion requires evidence for all 13 demonstrations, layout/scaling, packaging and required checks. A failed or unexecuted required item remains open. Clean-machine testing, signing and optional supplemental checks must be reported accurately without being inferred from a development-machine launch.
