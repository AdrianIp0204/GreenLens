# Versioned climate contracts and compatibility

These contracts are under implementation; they do not imply that the annual adapter or installed workflow has passed acceptance.

The original model `greenlens.model.v0.1`, static run/project scientific schema `0.1.0`, v0.2 display extension and static Radiance identity stay unchanged. New `greenlens.study.v0.3` distinguishes static prescribed overcast, weather-selected-hour and annual modes. The static path deliberately returns the original authoritative scientific input hash. No annual executable is needed to read old evidence. Future unsupported versions must be rejected explicitly, not coerced into current physics. Historical recipes dispatch only to known application implementations; imported command strings are never executed.

The compact `tests/fixtures/legacy-static-v0.1.zip` is the original licensed synthetic v0.1 A/B export, byte-for-byte, with its release digest and provenance in the neighboring JSON record. `scripts/legacy-replay.ps1` checks its digest before and after actual replay using a new local engine directory containing only `gensky`, `oconv` and `rtrace` plus the original libraries/runtime. It fails if either 77-sensor run fails or is omitted. The fixture contains no engine binaries or private source paths. Test execution status belongs in the progress/evidence ledger; the fixture's presence alone is not compatibility evidence.

Development climate adapters and profiles are provisional. Their failed investigations and immutable artifacts are preserved, but they are not published stable annual contracts. An unsupported development recipe must fail explicitly; its frozen original executable can reproduce its own integration evidence. The final v0.3 adapter identifier and complete profile become stable only after acceptance. This does not change support for published v0.1/v0.2 static evidence.

The bounded historical dispatch recognizes the exact method-2 patch-indirect recipe and method-3 explicit-solar recipe, each with its own complete allowlisted shipping/reference profiles, adapter identity, recipe schema, ground policy and process sequence. Recognition preserves inspection, metric derivation, copy/export and replay; it is not evidence that either numerical profile meets acceptance. Recorded commands are checked against compiled recipes and are never used as an executable script. Unknown methods, mixed method/schema/adapter identities and edited profiles are rejected.

Method 2 retains its original serialized profile without a `solar_ambient_divisions` key. Method 3 adds that explicit source sampling value. The optional Rust representation omits `None` when serializing historical profiles; readers additionally require canonical profile JSON, so an explicit null cannot silently change the original profile identity. Historical run, series, comparison, metric and project-summary fingerprints are not rewritten. A mixed-history replay discovers and verifies the actual pinned executable/library identity for each supported method and runs that method's compiled transport branch. The application's current profile constructors request method 3; recognized method-2 results remain historical even when their geometry and study role match current inputs. Test and native replay status are recorded separately in the progress ledger.

Weather binding records original EPW SHA-256, normalized EPW SHA-256, non-leap time-axis SHA-256 and a versioned interpretation. The provider reparses original bytes on opening a weather asset and compares normalized bytes and derived metadata; checksummed JSON alone is not proof of valid weather. Portable assets retain `original.epw`, `normalized.epw`, `weather.json`, `asset.json` (source/citation/license/rights) and `checksums.json`. Original local import paths are not stored. CLI inspection returns bounded metadata and summary, not all hourly records. The source profile is explicit and has no silent default.

Physical climate identity binds model geometry/materials, sensors, ground reflectance, weather/time policy, mode and requested numerical profile; finalized runs additionally bind exact adapter/engine/settings. The legacy prescribed exterior illuminance and display/name metadata are irrelevant to climate transport and excluded. Metric identity separately binds the immutable physical-result checksum and occupancy/threshold configuration. Changing metrics must derive new evidence or show a pending/stale state; it must not relabel old metrics. A/B compatibility checks occupancy/threshold semantics separately because different A/B result checksums correctly produce different metric identities.

Current-result lookup and offline report status also compare the complete retained numerical profile with the application's current request, including its compiled Radiance/adapter/method identity. The `shipping` or `reference` role alone does not establish currency. This check is separate from historical evidence validation: recognizing a historical profile in the future must not relabel it as the current profile. No immutable study, run, series, comparison or metric fingerprint is rewritten. The check uses the compiled pinned engine policy without requiring an engine installation; actual replay additionally requires equality with the complete installed engine/library identity.

## Compact output representation

`greenlens.timeseries.v0.3` is an application-owned format: explicit IEEE-754 float64 little-endian scalars in time, sensor, channel order. Each cell retains parsed raw visible RGB and derived lux `[R,G,B,E]`. This retains numeric engine output rather than ASCII whitespace/header formatting; generated recipes and process records retain interpretation. It does not enable or assume Radiance binary interchange on Windows.

Chunks contain at most 168 consecutive intervals and <=256 sensors. A full year has 53 chunks; the last has 24 intervals. Each maximum chunk is 1,376,256 bytes, far below the existing 64 MiB entry limit. A maximum-size A/B pair's numeric chunks total 143,523,840 bytes (136.875 MiB); weather, manifests, logs, reports and any additional runs still require complete export preflight against 256 MiB and 5,000 entries. This is a calculated storage bound verified with synthetic budget tests, not an observed simulation benchmark.

The manifest declares schema, shape, ordered sensor IDs, channels, units, precision/order and exact per-chunk counts/bytes/SHA-256. Readers validate contiguous shape, bytes, finite nonnegative values and RGB-to-lux consistency before exposing bounded hourly vectors or a selected sensor's 8,760-value series. Metric derivation consumes one chunk/hour at a time. Full matrices do not cross Tauri or become DOM tables. Partial writers do not create a complete series manifest. The outer finalized run must bind this content identity to immutable model/weather/time/engine provenance before project promotion.

Large coefficients, sky/sun matrices and octrees are regenerable scratch. Retained numeric chunks, weather and recipes must make inspection, copy, export and replay independent of that scratch. Selected-hour evidence contains one vector but its outer record retains the exact original interval index and source context, including the generator's preceding dew-point state.
