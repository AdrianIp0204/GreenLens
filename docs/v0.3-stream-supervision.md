# Isolated native streaming supervision preparation

This is infrastructure preparation for a possible future annual method. No production annual method calls `annual_stream::execute`; it changes no ray generator, numerical profile, method fingerprint or historical replay branch. No Radiance calculation is claimed by the synthetic tests below.

The Windows-only module requires Windows 10 or later for atomic Job assignment through `PROC_THREAD_ATTRIBUTE_JOB_LIST`. It launches a trusted executable with an argument array, child-only environment overrides, and an explicit inherited handle list. The kill-on-close Job is assigned before child execution. Standard output and standard error are bounded scratch files. Generated input uses one nonblocking byte pipe and a 64 KiB buffer, retaining every unwritten suffix. Its receipt counts and hashes only bytes accepted by successful pipe writes, and requires the exact finite record count.

One supervisor loop covers input generation, writing, parent exit, observed descendant lifetime, resource limits and cancellation. Success requires the complete input receipt, exit code zero and an empty Job with all observed members exited, followed by final file, scratch and stderr limit checks. This final scan covers writes occurring between the last live scan and exit. Failure terminates the Job and uses bounded cleanup; there is no input writer thread, pipe flush or unbounded join. Iterator steps must be trusted, bounded CPU work. The API cannot preempt arbitrary blocking Rust code. Deadline checks surround generation and resource sampling, so an individual filesystem operation is not claimed to be preemptible.

The implementation follows the documented [nonblocking byte-pipe partial-write semantics](https://learn.microsoft.com/windows/win32/ipc/named-pipe-type-read-and-wait-modes) and [atomic process Job assignment](https://devblogs.microsoft.com/oldnewthing/20230209-00/?p=107812). The existing production file-backed process path retains its previous launch mechanism; the new atomic launch is isolated pending method integration.

## Shared live scratch-size correction

The first native output-cap test exposed stale Windows directory-entry length while a child still held its growing output open: the entry appeared empty despite 131,088 bytes being written, and the intended 4 KiB cap reached the deadline instead. `process::scratch_sizes` now opens each regular file and obtains its current handle metadata. Existing depth, entry-count, symlink and reparse-point rejection remain in place. A regression observes two successive writes while the writer stays open, and the existing production 512 MiB cap test now tests both an open writer and an immediate successful child exit. The production annual path also enforces final file/scratch limits after retaining resource telemetry, before a successful process result. Resource rejection preserves a failure process record; cancellation preserves its existing diagnostics.

One local observation on 101 small files, over 20 complete scans, averaged **77.134 ms per scan**; subsequent verification reruns observed **88.468 ms** and **40.407 ms** for the same workload. These are workload-specific observations under the current machine load, not benchmarks or general timing guarantees. The supervisor sleeps 20 ms between iterations; complete scans, process queries and scheduling add to that interval. New annual telemetry states this explicitly. The exact previous policy string remains accepted when reading historical evidence and is never rewritten during validation.

## Verification

Run in the initialized native MSVC shell:

```powershell
. ./scripts/dev-env.ps1
cargo test --locked --offline -p greenlens-radiance --lib annual_stream -- --test-threads=1
cargo test --locked --offline -p greenlens-radiance --lib process::resource_tests -- --test-threads=1 --nocapture
cargo test --locked --offline -p greenlens-radiance --lib process:: -- --test-threads=1
cargo test --locked --offline -p greenlens-radiance --lib resource_policy_preserves_exact_historical_records
cargo clippy --locked --offline -p greenlens-radiance --all-targets -- -D warnings
```

The six streaming tests exercise slow partial/zero-progress writes with byte/count/hash agreement, argument quoting and child-only environment, immediate parent exit with a descendant retaining the pipe, early stdin exit, cancellation, producer errors, malformed stream lengths, memory/output caps and invalid preflight parameters. Helper test entry points are explicitly invoked by these tests; their standalone ignored status does not represent skipped verification. The two resource tests exercise live size growth and termination of the actual synthetic process tree. A separate synthetic metadata test accepts both exact known policy strings, preserves historical serialized bytes and rejects unknown wording.

Initial failures and their remedies were retained in local verification scratch: descendant lifetime needed observed process handles in addition to Job membership, and open output sizes needed handle metadata. Scoped results were 6 streaming tests passed, 5 process tests passed (including the 2 resource tests and both cancellation paths), and 1 metadata-policy test passed; strict crate all-target Clippy passed. The immediate-exit oversized fixture was rejected with exit code zero, but its observed failure was caught by a live sample; the narrow post-scan race is additionally closed by the final source-level guard, not claimed to be deterministically recreated by that timing-dependent fixture. Test diagnostics are under `%LOCALAPPDATA%/GreenLens/verification`, never source or portable scientific evidence. These checks do not qualify a numerical annual method, prove real-engine streaming behavior, or satisfy final installed application and CI acceptance.
