# Climate study commands — implementation candidate

The headless climate services are implemented. The current [method-4 repeated-coefficient transport and profiles](v0.3-scientific-method.md) remain under scientific investigation; these instructions do not claim release acceptance. The [controlled reference protocol](v0.3-reference-protocol.md) defines separate qualification of the numerical reference before candidate comparison. Methods 2 and 3 remain available only through their recognized historical inspection/replay paths; their retained failures are not method-4 acceptance. See [progress](progress.md) and the [implementation plan](v0.3-implementation-plan.md) for individual outcomes, including failures and installed candidate observations. Legacy static commands and immutable evidence remain supported.

## Build and inspect local weather

From a checkout in PowerShell 7.5 or newer (the climate verification scripts preserve timestamp strings using `ConvertFrom-Json -DateKind String`):

```powershell
. ./scripts/dev-env.ps1
cargo build -p greenlens-cli --locked
$cli = Join-Path $env:CARGO_TARGET_DIR 'debug/greenlens.exe'
& $cli doctor
& $cli weather inspect ./examples/weather/pvgis-hong-kong-tmy-2005-2023.epw --source-profile pvgis-tmy
```

`doctor` checks the legacy engine installation. Climate execution additionally verifies its exact annual executable/library inventory before starting. Install the pinned separate engine with `./scripts/install-radiance.ps1` if needed. Initial dependency acquisition uses the network; importing retained weather, simulation, inspection, comparison and replay do not.

For an extracted CLI distribution, use `$cli = Join-Path $PWD 'greenlens.exe'` from its root directory and continue with the weather commands; a runtime user does not need Cargo, Node.js or a source checkout. The distribution retains the referenced examples and source declarations. Engine acquisition from source and verification scripts are separate development steps described in [installation](installation.md).

The reviewed example is reanalysis-derived typical weather near Hong Kong, not a measured station record or a forecast. Its source-specific time policy and rights are in `v0.3-weather-sources.md`. Every import requires an explicit source profile and citation/license record. Required missing weather is an error, even at night.

## Portable A/B study

In the desktop, **Results: current study / Static history / Climate history** changes inspection only. Run continues to use the accepted study in Analysis. Historical tables use saved coordinates and values, identify mismatches, and suppress overlays on different current geometry. Historical climate time series have their own saved-sensor selector; they do not select a same-ID sensor at a different current position. Switching the scientific study does not remove retained evidence or require changing it back just to inspect history.

Choose new destinations. The following example uses the original 77-sensor room, within the climate limit of 256; the separate release verification scripts use an explicitly documented 24-sensor grid to measure profiles.

```powershell
$project = Join-Path $env:LOCALAPPDATA 'GreenLens/projects/climate-example'
$asset = Join-Path $env:LOCALAPPDATA 'GreenLens/imports/pvgis-example'
& $cli example $project
& $cli weather import ./examples/weather/pvgis-hong-kong-tmy-2005-2023.epw $asset --source-profile pvgis-tmy --source-record ./examples/weather/pvgis-hong-kong.source.json
& $cli weather attach $project $asset
& $cli study configure $project ./examples/climate-study-pvgis.json --alternative A
& $cli study configure $project ./examples/climate-study-pvgis.json --alternative B
& $cli study run $project --alternative A
& $cli study run $project --alternative B
```

Each successful `study run` returns job-status JSON containing its immutable result ID and provenance. Inspect the returned `climate_result.id` for a climate run; configuration/import commands instead return their relevant study or weather metadata. Progress is written to stderr. Ctrl+C requests supervised process-tree cancellation; cancelled/failed output cannot become a completed run. `study run` uses the saved alternative's study. The study JSON selects annual versus `weather_hour` (with `interval_index` 0–8759), its retained weather binding and numerical profile. A selected-hour run retains one vector at its actual weather index; it does not masquerade as a year. These annual commands perform full transport; provisional profiles may take hours, and small-fixture timings are not a runtime promise.

Use the returned IDs for inspection and explicit historical comparison:

```powershell
$a = 'replace-with-completed-A-run-id'
$b = 'replace-with-completed-B-run-id'
& $cli result $project $a --hour 1908
& $cli result $project $a --sensor s000001
& $cli study compare $project $a $b --interval 1908
& $cli study compare $project $a $b --field da
$copy = Join-Path $env:LOCALAPPDATA 'GreenLens/projects/climate-copy'
& $cli copy $project $copy
$package = Join-Path $env:LOCALAPPDATA 'GreenLens/projects/climate-evidence.zip'
& $cli export $copy $package --run $a --run $b
& $cli replay $package
```

Use a sensor ID from the returned ordered sensor list; `s000001` is the first generated sensor. Metrics support `da`, `cda`, `udi`, `underlit` and `overlit` for complete annual results. A selected-hour result accepts only its retained original interval index and has no annual metric vector. Hourly differences are lux; metric differences are percentage points. A/B comparison rejects incompatible weather, sensors, time axis, schedule, thresholds, engine or numerical settings. Different profile results belong in a convergence check rather than a design comparison.

`study metrics PROJECT RUN SETTINGS_JSON` rederives metrics without new transport and returns a distinct metric identity. Its JSON uses the `metrics` object shape in the example study. Default occupancy is every day [08:00,18:00) local standard time, with no inferred weekdays. An explicit `{"kind":"mask","weights":[...]}` requires exactly 8,760 values in [0,1] and a positive sum. Occupied nighttime remains in the denominator.

Export explicitly selects run snapshots and includes portable weather, raw-RGB/lux chunks, inputs, recipes, annual metrics where applicable, provenance, checksums and an offline report. It excludes engine binaries and disposable matrices/octrees. Full Save As copies referenced evidence rather than changing a path. Reopening, inspection and export require no original imported weather or scratch. Replay requires the compatible separate engine and only executes the application's recognized adapter; imported command strings are never executed. Climate replay checks every retained interval/sensor against `max(0.5 lx, 0.5% of reference)`; legacy static replay retains `max(0.1 lx, 0.1% of reference)`. See [replay and historical dispatch](replay.md). Replay agreement is integration verification, not acceptance of a provisional physical method.

## Original synthetic fixture

```powershell
$synthetic = Join-Path $env:LOCALAPPDATA 'GreenLens/imports/synthetic.epw'
New-Item -ItemType Directory -Force -Path (Split-Path $synthetic) | Out-Null
& $cli weather synthetic $synthetic
& $cli weather import $synthetic "$env:LOCALAPPDATA/GreenLens/imports/synthetic-weather" --source-profile epw-hour-ending --source-record ./examples/weather/synthetic.source.json
```

Synthetic bytes are deterministic and explicitly non-climatic. Use the returned binding when constructing its study; the PVGIS study binding must not be reused for different weather.

## Desktop candidate workflow

Build the unsigned, per-user Windows installer and CLI from the checkout:

```powershell
. ./scripts/dev-env.ps1
cargo build -p greenlens-cli --release --locked
Push-Location apps/desktop
npm ci
npm run tauri -- build --bundles nsis
Pop-Location
node scripts/license-inventory.mjs --strict --check --installer-cache "$env:LOCALAPPDATA/tauri/NSIS"
./scripts/package-artifacts.ps1
& "$env:CARGO_TARGET_DIR/release/bundle/nsis/GreenLens_0.3.0_x64-setup.exe" /S
& "$env:LOCALAPPDATA/Programs/GreenLens/greenlens-desktop.exe"
```

The installed app uses its bundled frontend, with no development server. It requires WebView2, the compatible Microsoft Visual C++ v14 x64 runtime and the separately installed pinned Radiance package. Initial dependency acquisition is online; ordinary calculation is local. A package named 0.3.0 is still a development candidate until all verification items are satisfied.

1. Open a portable project, or create the synthetic room and Save to a new folder. Analysis → Configure study and import weather contains the study draft.
2. Choose Import local EPW, select the file using the native dialog, select its documented source time profile and inspect the quality/time policy. For the supplied real example select **PVGIS TMY**, then load `examples/weather/pvgis-hong-kong.source.json`. Retain the weather to copy original bytes and the source declaration into the project.
3. Choose static overcast, selected weather hour or annual daylight. Selected hour accepts a retained interval index or a month/day/hour-ending lookup. Annual studies expose daily occupancy or an explicit mask, DA/cDA threshold and UDI bounds. Apply creates one Rust-validated document transaction; an unapplied draft does not change what Run calculates.
4. Use Run in the top toolbar. Stage messages and Job logs identify the active native work; Cancel joins the process tree. No percentage completion is invented for a sampling process.
5. Choose Analysis display mode and a completed result snapshot. The newest matching current study uses current metric conventions derived in Rust; explicit historical snapshots use their saved conventions. A mismatched historical result remains inspectable in its table and is suppressed on current geometry.
6. Scrub saved hourly values with the slider, interval field or calendar lookup. This reads retained chunks without calculating again. Select a sensor for its retained time series. DA, cDA, UDI, underlit and overlit use percent of occupied time, with an unweighted sensor summary explicitly distinguished from area.
7. Configure/run the other alternative. A/B compare selects immutable snapshots independently of the main result selector, uses synchronized hours/shared lux scales, and shows metric differences in percentage points. Weather/time/metric conditions belong to that selected pair. Incompatible pairs are rejected by Rust.
8. Save As makes a complete portable copy. Export selects explicit saved run IDs and writes a native-selected ZIP destination. The report describes the selected runs' immutable metric settings; current derived display settings do not silently rewrite their evidence. Use the distributed CLI `replay` command on that ZIP.

Calendar lookup is also available headlessly:

```powershell
& $cli weather find-hour $project 'replace-with-retained-weather-id' --month 12 --day 31 --hour-ending 24
```

Hour 24 denotes the next midnight at the end of that labeled weather day. No OS timezone, daylight saving or inferred weekday schedule enters the lookup. Invalid non-leap dates are rejected rather than normalized into another date.

## Required verification entry points

`scripts/climate-cli-integration.ps1 -Mode WeatherHour -Replay` exercises real selected-hour A/B, complete copying, original-source/scratch unavailability, selected export and replay. `-Mode Annual` requires all 8,760 intervals rather than extrapolation. `scripts/annual-convergence.ps1 -ReplayShipping` runs both full-year alternatives at shipping and reference profiles and records every frozen per-sensor metric check. These commands fail on missing engines or incomplete outputs. Their existence is not evidence that the final acceptance suite passed.
