## Renderer and data boundary

The candidate renderer is upstream Typst **0.15.1**, Windows x64/MSVC, source `9dfd3a08500b7896045f907433cf7b4b02434fad`. The [dependency manifest](../dependencies/typst.json) pins the official ZIP, every extracted member, executable and two font files. The renderer is installed separately beneath `%LOCALAPPDATA%/GreenLens`; neither executable nor font binaries are checked into source or bundled in the current application.

The original [template](../reports/energy/feasibility.typ) reads only a fixed local JSON filename and two fixed local SVGs. JSON strings become text, never Typst source, `eval`, imports, commands or asset paths. The shared Rust service validates `EnergyReportData`, supplies every value and display string, stages owned templates/assets and invokes Typst through supervised argument arrays. It never executes templates or recipes supplied by an evidence package. The Gate 0 `greenlens.energy-renderer-fixture.v1` schema is deliberately separate from that production DTO.

Compilation uses `--root .`, `--ignore-system-fonts`, `--ignore-embedded-fonts`, an explicit pinned font directory, fresh empty package/cache directories, fixed creation timestamp and one compilation worker. The owned template has no package imports. Process-local HTTP/HTTPS proxies point to an unavailable loopback endpoint; caller environment is restored. This is an offline dependency-closure test, **not an OS network sandbox**: Typst has no `--offline` flag, and arbitrary templates remain out of scope. The compiler's dependency output was checked against the exact four owned input files. An explicit attempt to read outside the staging root failed with no PDF.

Production uses the shared Rust process supervisor, bounds recursive staging/output bytes, rejects unsafe assets and unrecognized DTOs, and preserves failed output separately. The feasibility wrapper reuses the existing Windows atomic Job supervisor on its flat, fixed staging set: 120 seconds per positive compile, 2 GiB sampled runner-plus-job memory, 256 MiB scratch and 64 MiB per output. These are feasibility ceilings, not measured maximum-building budgets. The native Job was empty and all streams closed after every process, including the expected negative test.

## Actual renderer checks

Run installation explicitly, then the native feasibility command:

```powershell
pwsh -NoProfile -File scripts/install-typst.ps1
pwsh -NoProfile -File scripts/energy-report-feasibility.ps1
```

Installation is the only network acquisition step. Already reviewed ZIP/font downloads can be supplied using `-ArchivePath` and `-FontCacheDirectory`; the font cache must contain the two named OTFs and `NotoSansCJK-OFL.txt`. Generation never invokes the installer. A missing or changed executable/font fails before rendering. The final test additionally used a renderer installation named `Typst 0.15.1 空間` and report staging with spaces/non-ASCII characters.

The actual output is an eight-page, 152,020-byte tagged PDF and eight native PNGs. Two identical PDF compilations were byte-identical. The final compile and PNG export took approximately 0.53 and 0.64 seconds respectively on this machine; sampled runner-plus-job memory peaked at 281,481,216 bytes, including the PowerShell host. These timings are observations, not portable performance guarantees.

All eight PDF pages were independently rasterized with Poppler and visually inspected. The 96 input rows are present exactly once and in order, with repeated headings on pages 3–7. Traditional Chinese, Latin, units and six hostile strings survived extraction. Both selected fonts are embedded with Unicode maps. There is no PDF JavaScript/open action or escaped-root sentinel. The long final inventory page intentionally has unused space. Initial installer property-count and empty-environment-option failures, plus the earlier unlabeled chart draft, remain in external evidence; they are not counted as successful attempts. Python/pypdf and Poppler were independent development audit tools only; the report generation command itself requires neither.

## Fonts and redistribution review

Only unmodified **Noto Sans CJK TC 2.004 Regular/Bold**, pinned to official source commit `523d033d6cb47f4a80c58a35753646f5c3608a78`, are enabled. Their embedded names retain Adobe's 2014–2021 copyright. The [SIL OFL 1.1](../reports/energy/notices/NotoSansCJK-OFL.txt) permits embedding and redistribution with its notices; generated documents are not required to adopt that license. No renamed or modified font is used. Traditional Chinese and Latin are tested; other writing systems and mathematical coverage are not yet established.

Typst's top-level [Apache license](../reports/energy/notices/Typst-LICENSE.txt) and [NOTICE](../reports/energy/notices/Typst-NOTICE.txt) are retained. That NOTICE is not a complete target-feature dependency inventory. The official binary also embeds assets even though this template disables their use. The separate [typst-assets notice](../reports/energy/notices/Typst-assets-NOTICE.txt), from checksum-verified crate 0.15.1, includes OFL, GUST, Bitstream/DejaVu, CC0, W3C, PDFium and NewComputerModern terms; NewCM10-Regular specifically names GPL-3.0-or-later with Font and Distribution Exceptions. Do not describe the whole binary as Apache-only or infer that disabling fonts removes distribution obligations.

The pinned source lockfile has 425 workspace packages. The [Windows target-source inventory](evidence/v0.4-energy/report-typst-target-inventory.json) follows the actual release command with default features and `self-update`: 343 reachable normal/build packages, comprising 327 registry archives verified against the lockfile and 16 upstream workspace crates. Dev dependencies and other target branches are excluded. The [deduplicated notice catalog](../reports/energy/notices/Typst-target-NOTICES.txt) retains 231 original texts; missing per-crate root notices were obtained from the exact upstream commits. This is a source dependency inventory, including build-time crates, not a linker map or a reproducibly rebuilt official executable. Resolution used installed Cargo 1.99.0 against the unchanged lockfile; the release workflow selects Rust 1.95.0.

The review identifies MPL-2.0 `option-ext` source-access obligations, permissive notice requirements, and unchanged embedded-asset terms. `glidesort` provides its explicit dual-license grant in README rather than a dedicated license file; that grant and the full standard Apache text are retained. The Windows `lzma-sys` build selects 73 bundled liblzma C files: 71 carry public-domain declarations and two generated tables bind public-domain generators. GPL/LGPL command-line utilities and build scripts in that source archive are not selected by this build list. The conservative notice catalog does not imply that every source/test notice governs the executable.

Actual binary imports include Windows APIs, Universal CRT and `VCRUNTIME140.dll`, supplied by the host environment. No DLLs are copied by this work. Rebundling would still require binary/source correspondence, Rust runtime/compiler attribution, source-access placement and complete embedded-asset distribution compliance. Binary redistribution remains unapproved; separate user acquisition of the unchanged official binary and pinned fonts is supported.
