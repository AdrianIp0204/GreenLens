# v0.7 derived study revisions and report issues

These contracts supplement the unchanged thermal, study, run and architectural-scope contracts. They do not change a physical simulation identity, confer qualification, or rewrite retained run evidence. The [specification](v0.7-spec.md) and [acceptance ledger](v0.7-acceptance.md) distinguish implemented contracts from tested delivery.

## Scope storage and compatibility

`ArchitecturalProject.scope_history` is optional and omitted when absent. Its schema is `greenlens.scope-history.v1`, with an append-only `revisions` array and optional `active_revision_sha256`. The existing `scope` field remains the compatibility projection: when active, it must exactly equal the selected revision's scope; when cleared, it must be absent. Reading an older project creates neither history nor a new file. Explicit acceptance, clearing or legacy restoration may adopt its exact scope into history. No read-time migration occurs.

Each `greenlens.scope-revision.v1` retains:

- A content identity, optional earlier parent and the exact carry-forward plan identity and review decisions.
- The complete admitted reference manifest, portable asset ID and digest of the actual serialized retained manifest. A canonical JSON digest does not substitute for that file digest.
- Exact A/B `ThermalModel`, calendar and optional `EnergyStudy` snapshots. Missing study is explicit, allowing documentation before weather assignment. A retained study must use its retained calendar.
- The unchanged version-1 `ArchitecturalScope`, including mappings, assumptions, reconciliation, coverage and report-view definitions.
- A deterministic supported-input provenance checklist derived from those exact inputs and declarations.

No revision stores machine paths or runtime receipts. Its identity hashes its versioned complete content with the identity field empty. Parent verification recomputes the carry-forward proposal and acceptance; changing a record and merely resealing its hash cannot create a valid inconsistent provenance checklist or review history.

History is limited to **64 revisions**. A project containing scope history is limited to **16 MiB of the pretty-printed manifest including its trailing newline**; capacity may be reached before 64 records. Core admission separately limits a revision to 32 MiB, a carry-forward proposal to 16 MiB, and each provenance/review collection to 65,536 rows. Existing architectural limits remain, including eight reference revisions, 20,000 mappings, 2,048 assumptions, 4,096 reconciliations, eight report views and the existing scope string/byte limits. Review rationales are at most 2,048 bytes and decision row IDs must be unique. These maxima are resource bounds, not promises that every maximum-sized combination fits a project.

No history or asset is silently pruned. The candidate is rejected before publication if it exceeds capacity or loses a required reference. Earlier legacy file-admission limits remain unchanged; new history does not increase them. Shared portable archive limits remain **5,000 entries, 64 MiB per entry and 256 MiB uncompressed**. Save As retains every admitted reference asset, including assets required by historical revisions. Scope snapshots are inline manifest data; reference chunks remain normal bounded evidence files. Successful publication uses the existing one-writer lock, expected manifest revision and atomic replacement.

## Reviewed carry-forward

`greenlens.scope-carry-forward.v1` binds a particular parent revision to the exact current reference and analytical context. It contains a proposed scope and stable review rows. Rows identify their kind, semantic key, unchanged/changed/deleted/added/unresolved state, before/after values, review requirement and explanation. An accepted request supplies the exact plan digest, complete candidate scope and explicit `reviewed` or `unresolved` decisions with rationale. Rust recomputes the plan; a changed context rejects a stale preview. Every required row needs a decision. Unknown/duplicate decisions are rejected. An unresolved decision cannot accompany a supposedly resolved mapping, source declaration, reconciliation, figure or whole-building conclusion.

Geometry correspondence uses generated semantic geometry, parent relationships, topology and boundaries, separately from the broader snapshots used for editing locks. COP-only changes can therefore retain unchanged geometry mappings and view frames while rebinding them only in the accepted new revision. Changed input/source declarations still require review. A previous declaration is not evidence for a newly applied value: a changed assumption is proposed as missing, with its old source value preserved in the immutable parent and the review's before value. The new applied value is displayed separately.

Geometry changes clear affected mapping targets and invalidate affected reconciliation/views. A reference revision or accepted coordinate-transform change receives strict source reconciliation. Revision-scoped occurrence IDs are not matched by names. Added occurrences begin unresolved; deleted occurrences and targets remain identifiable in the review and parent. Coverage is reset to an explicit unknown state where its geometry/source basis changed, and a former whole-building claim requires renewed explicit review.

The shared runner service returns a complete candidate `Project` without disk writes. Cancellation and failed validation return no accepted candidate. `initialize_scope` permits same-context scope editing and explicit legacy adoption; changed scientific/source inputs require `prepare` then `accept`. `activate` moves only the active history pointer and compatibility projection. It neither edits scientific inputs nor appends/prunes history. New UI undo entries should retain the exact active revision hash, because equal scope text can occur in different exact contexts. Legacy value-only history remains interpretable without rewriting its entries.

An old scope whose inputs differ from the current model can be adopted only when its exact model snapshots remain available in integrity-checked retained evidence. Names, current geometry or approximate matching are not substitutes. If those snapshots are unavailable, the action fails with a recovery explanation and preserves the old document.

## Supported-input provenance

The `greenlens.input-provenance-checklist.v1` inventory traverses actual model, calendar and optional study fields, including site, zone geometry, boundaries, constructions/materials/glazing, gains, HVAC/fan/ventilation, curves, schedules, windows and shading. Rows contain stable object/field identity, authoritative applied value, units where defined, declared source information and applicable full source declarations. Source information and applied numerical values remain distinct.

Statuses are `unreviewed`, `documented`, `measured`, `assumed`, `synthetic`, `missing`, `not_applicable` or `conflicting`. A citation embedded in a material or schedule does not automatically establish provenance review. An empty assumption register produces unreviewed rows, never complete provenance. Conflicting declarations are disclosed. The inventory preserves exact ten-minute schedule values; it does not invent interpolation or infer source quality.

Documentation completeness is a reporting disclosure. Missing or unreviewed provenance does **not** prohibit otherwise preflight-valid Unassessed execution. Execution completion, evidence integrity, relationship to current inputs, numerical sensitivity and scientific assessment remain separate. None of these records restart or relabel the stopped daylight or real-weather qualification protocols.

## Report content and issuance boundaries

`greenlens.energy-report-issue-content.v1` is the deterministic report content contract. It retains the canonical `EnergyReportWorkbenchData`, selected exact scope revision and scope assessment, optional exact-pair sensitivity, aligned figure definitions, renderer identity and requested PDF inclusion. The scope's model/calendar and any retained study must match the actual selected report cases. Figures bind the selected run/record, scope revision, unchanged scope content identity and retained view. Other-pair sensitivity is rejected, not reassigned.

The current owned renderer identity is `greenlens.energy-report-issue-renderer/1`, with document schema `greenlens.energy-document.v0.7`. It includes owned template digest, audited Typst version/executable digest, local font digests, aligned-figure method, HTML method, fixed PDF creation time, PNG resolution and disabled system/embedded-font settings. Runtime execution times and local executable paths stay outside deterministic content identity. Content is bounded to 48 MiB before the unchanged 64 MiB archive-entry limit. The implemented shared issuance store permits at most **32 issues**, a **256 KiB index**, and **252 deterministic products per issue**, leaving space for the product manifest, runtime receipt and checksum seal. Limits are checked before publication; none authorizes pruning earlier issues.

Issued artifact bytes and member hashes are retained independently of whichever design/scope is later active. Exact regeneration requires the recognized renderer/template/font identity; an unavailable old renderer is an explicit regeneration limitation, not permission to update the issue. Historical run/report bindings and earlier renderer identities are preserved. Descriptive profile text is not a rendered preview, rendering success is not physical qualification, and missing exact-pair sensitivity remains a material disclosure.

## Snapshot-bound figures

`greenlens.aligned-reference-figure.v2` and method `greenlens.reference-analytical-orthographic/2` are additive; the earlier v1 figure renderer remains available unchanged. Each request retains its exact view, selected run and record hashes, scope revision/content hashes and optional focused occurrence IDs. It renders the **selected run's** thermal model/calendar, never the active editor model. Reference and analytical geometry share the orthographic frame and section. Definitions retain counts, represented occurrences, analytical objects, labels, scale, caption, limitations, SVG digest and definition digest.

The renderer reads the complete admitted triangle stream, applies view/section clipping first and then performs deterministic reduction. It protects visible mapped/focused components and one representative of every visible occurrence. Limits are 8,000 visible retained reference triangles, 16,384 analytical edges, 256 explicit focus occurrences, 8 MiB SVG output and a 30-second per-view deadline. If protected geometry exceeds the budget, it emits an explicit unavailable figure instead of a misleading partial or empty close-up. Labels are bounded and collision-aware; no filled cut faces, hidden-line resolution or spatial thermal field is claimed. North remains unknown unless the retained source transform declares it. Legacy global stride sampling is not used by v2.

## Immutable issue storage and publication

`Project.report_issues` is optional and absent in legacy projects. `greenlens.report-issue-index.v1` contains summaries with exact scope/reference, A/B records and optional sensitivity-session/run references, plus title/revision and output-family selection. An issue's deterministic ID is the canonical hash of `(INDEX_SCHEMA, content_sha256, products_sha256)`. It therefore binds **both** frozen content and generated product digests; changing and resealing a product cannot retain the old issue ID. The pre-render content identity is separate. Receipt timestamps do not change either deterministic identity.

Each issue occupies `report-issues/<issue-id>/`. `issue-content.json` contains the frozen content, `issue-products.json` (`greenlens.report-issue-products.v1`) contains the sorted product path/byte/hash inventory and its identity, `issue-runtime.json` contains structured UTC/timing/resource/process-completion observations, and `checksums.json` seals the exact member set. The portable receipt excludes executable paths, arguments, environment blocks and free-form errors. A full local renderer receipt remains in external scratch. No raw imported SVG or HTML is executed by the desktop product viewer.

Issuance verifies retained cases/reference assets, builds from the explicitly selected revision, renders into external staging, validates complete requested output families, preflights the entire retained project's shared archive budget, copies through a temporary project destination and promotes it before atomic manifest publication. The one-writer lock and expected manifest revision remain mandatory. Stale client or undo snapshots cannot remove or rewrite old summaries or scope revisions. Scope/run/asset dependencies cannot disappear from an issued project's manifest.

A conflict after completed rendering leaves a bounded UUID recovery token in local staging and does not advertise the issue as accepted. Recovery is explicit: reload or reconcile the external document, preserve drafts, then publish the staged issue using the fresh expected revision. It cannot silently merge or rebind the completed content. Cancellation leaves the previous accepted manifest intact; unadvertised staging may remain for diagnosis/recovery.

Inspection reads actual bytes, validates the exact seal and product inventory, checks retained scope and case records, and checks canonical JSON/CSV/geometry products and aligned SVG hashes against frozen content. It requires the requested HTML/PDF families, and a contiguous bounded PNG sequence for PDF issues. Reuse during project opening uses that operation's already decoded and content-fenced run records; it does not repeat numerical extraction for each issue. Listing only index metadata is explicitly weaker than this verification.

These hashes establish content integrity and reproducible bindings, **not author authenticity or professional approval**. A wholly substituted project with newly computed identities is a different document, not an authenticated original. No signature is invented. Native PDF/PNG appearance and pagination need their separately recorded renderer/page review; hashes alone do not establish readable pages or physical validation.

Regeneration verifies the selected issue and exact supported renderer identities, rebuilds figures from its retained reference and analytical snapshots, and renders to fresh external staging. It requires the complete new product-manifest identity to equal the original before copying to a new chosen destination. It never overwrites issued products and never starts EnergyPlus. If the exact template/font/renderer is unavailable, preserved products remain inspectable and the limitation is reported. The original runtime receipt remains unchanged; a new local rendering receipt describes the new process separately.

## Portable issued-project export

### Numeric transport compatibility

The v1 scope revision serializer and identity are unchanged. JavaScript serializes an integral floating-point number such as `600.0` as `600`. The reader restores this representation only for scalar checklist `applied_value` fields that exactly equal the checklist derived from the retained typed analytical snapshots, within JavaScript's safe-integer range. It then requires the complete checklist to match, including source declarations, order, status and counts. Changed values, unknown or duplicate metadata, nonfinite values and exceeded bounds reject. This is a transport compatibility repair, not permission to normalize or rewrite retained evidence. The accepted serialized bytes and identity remain those of the original revision.

`greenlens.issued-project-export.v0.7` exports the **complete saved project**, all retained runs/weather, normalized reference assets, scope history, sensitivity sessions, issue products and their exact dependency closure. It requires a saved manifest identical to the supplied document and rejects excluded evidence attachments rather than silently omitting or leaking them. The package explicitly remains a normalized-reference/analysis archive; it does not include an external proprietary architectural source.

The exporter performs ordinary cancellable full verification, binds its actual member inventory to that content snapshot, and preflights the same **5,000 entries / 64 MiB per entry / 256 MiB uncompressed** rules used by the reader. It then copies verified members to owned external staging and writes a new ZIP. There is no automatic subset or history-pruning fallback. The reader rejects unsafe paths, duplicate/case-alias entries, symlinks, directory entries, undeclared members, size overruns, mismatched seals and inconsistent scope/issue dependencies. Extraction uses a new destination and performs ordinary full project verification. Inspection does not require simulation or report engines.

Replay takes an explicit retained issue ID and runs only its A/B snapshots through the recognized compiled EnergyPlus recipe and unchanged integration tolerance. It does not execute imported commands, expand the replay set to unrelated history, or claim numerical sensitivity/physical qualification from equality. Required native engine absence is an error.

## Shared CLI workflow

These commands use the same Rust revision services as desktop actions. They perform one cancellable project intake, display honest verification progress on stderr, return JSON on stdout, and save accepted mutations with the originally read manifest revision. Ctrl+C before publication preserves the accepted document. Input JSON uses the existing bounded reader and the stricter core contract validation; imported command strings are never executed.

```powershell
greenlens reference revisions .\project
greenlens reference revisions .\project --revision <revision-sha256>
greenlens reference scope-apply .\project .\initial-scope.json
greenlens reference scope-review .\project --parent <revision-sha256>
greenlens reference scope-accept .\project --parent <revision-sha256> --plan <plan-sha256> --scope .\reviewed-scope.json --decisions .\decisions.json
greenlens reference scope-activate .\project --revision <retained-revision-sha256>

greenlens report-issue create .\project --a <baseline-run-id> --b <proposed-run-id> --scope <scope-revision-sha256> --typst-dir <local-typst-directory>
greenlens report-issue create .\project --a <baseline-run-id> --b <proposed-run-id> --scope <scope-revision-sha256> --html-only
greenlens report-issue list .\project
greenlens report-issue inspect .\project <issue-id>
greenlens report-issue regenerate .\project <issue-id> .\new-output-directory --typst-dir <local-typst-directory>
greenlens report-issue recover .\project <local-recovery-token> --expected-revision <fresh-project-file-sha256>
greenlens report-issue export .\project .\new-issued-project.zip
greenlens report-issue inspect-package .\new-issued-project.zip
greenlens report-issue replay .\new-issued-project.zip <issue-id> --engine-dir <local-energyplus-directory>
```

`scope-review` prints the complete proposal; the caller retains its `plan_sha256`, reviews required rows and prepares the full candidate `proposed_scope` plus decisions. A decisions file is an array of `{ "row_id": "<row-sha256>", "resolution": "reviewed", "rationale": "Actual review explanation" }`. This is an explicit document action, not automatic acceptance of generated assumptions. The normal desktop workflow presents these fields without requiring JSON editing.

`scope-activate` requires an explicit retained ID; it cannot silently select the latest revision. `revisions` lists only retained documentation unless `--revision` requests one complete snapshot. A legacy scope without history is identified explicitly. The legacy scope context/assessment/import commands remain supported.

`report-issue create` returns the published project revision and an inspection containing the product-bound `summary.id`; do not substitute `content.content_sha256` for that ID. Create/recover optionally accept `--expected-revision`. `list` admits only index metadata and directs the user to `inspect` for actual product/case verification. Regeneration/export destinations must be new. `--html-only` declares a different deterministic output family; it is not permission to silently omit requested PDF/PNG products. Existing engine/Typst discovery settings remain supported, and machine-specific paths never enter portable content.

## Dependencies and schema authority

This phase adds no Cargo/npm runtime dependency, new engine or redistributed binary/font. Original renderer/template code remains Apache-2.0 and reuses the separately installed pinned Typst and reviewed Noto fonts in `dependencies/typst.json`, together with existing native process supervision. See [dependency review](dependencies.md). The JSON schemas for [scope revisions](../schemas/scope-revision-v0.7.schema.json) and [issue indexes](../schemas/report-issue-index-v0.7.schema.json) document wire shape; Rust additionally enforces complete hashes, content/reference membership, canonical serialization, applied-input provenance, capacity, actual byte integrity and publication rules. Existing v0.6 scope and thermal/study schemas are not rewritten.

## Verification boundary

Core and runner regressions cover COP retention, geometric/deleted targets, strict reimport, empty provenance, stale/duplicate decisions, resealed claims, legacy read without mutation, explicit clear/restore, cold portable copy, cancellation and bounded capacity. These are document/integrity regressions, not engine or installed-native acceptance. Exact source-bound results, report page reviews, real-engine observations and remaining blockers belong in the acceptance ledger and evidence records; contract implementation alone does not establish release completion.
