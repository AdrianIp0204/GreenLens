## Workflow

Open a retained project, inspect its reference and analytical scope, and select actual baseline/proposed runs. Reference selection and historical mapping inspection are separate. In the Reference workspace, adopt or accept a scope revision, then use **Review changes and carry forward** after an input change. Review each affected row before accepting a new revision. Unchanged geometry mappings can survive a COP change; a reference reimport or geometry change requires explicit reconciliation. Drafts are not accepted inputs.

In Reports, select the exact run pair and scope revision before issuing. The issue freezes that evidence, report metadata, figure definitions and renderer identity. Older issues retain their original inputs and products after later edits. The provenance checklist distinguishes documented sources from applied values and incomplete documentation. Missing exact-pair sensitivity and Unassessed science remain visible.

Issue history provides integrity-checked figure/image previews and access to actual retained PDFs. Complete portable export includes all accepted history and required normalized assets within the shared bounds. It is not an archive of an original external proprietary model. Excluded private attachments require an explicit inclusion decision; export does not silently include them or prune required history. Save As preserves the complete admitted project.

## Launch and shared CLI

The installed path remains:

```powershell
& "$env:LOCALAPPDATA/Programs/GreenLens/greenlens-desktop.exe"
```

That command launches whichever candidate is installed. Consult the identified candidate receipt before attributing observations to v0.7. Windows packages are unsigned. WebView2 and Visual C++ runtime requirements remain in [installation](installation.md); a clean-machine check is a separate outstanding claim.

Development, with one build owner:

```powershell
. ./scripts/dev-env.ps1
cargo build --release --locked -p greenlens-cli
$cli = Join-Path $env:CARGO_TARGET_DIR 'release/greenlens.exe'
& $cli --version
& $cli report-issue --help
Push-Location apps/desktop
npm run tauri -- dev
Pop-Location
```

The development server is not installed-native evidence. Native calculation/replay uses the separately installed compatible EnergyPlus; PDF/PNG rendering uses pinned Typst and fonts. Inspection of retained issued products needs neither engine nor original weather/source paths. No network is needed for normal operation.

Example shared-service commands, substituting actual IDs returned by inspection:

```powershell
& $cli reference revisions ./project
& $cli reference scope-review ./project --parent $scopeId
& $cli report-issue create ./project --a $baselineRun --b $proposedRun --scope $scopeId
& $cli report-issue list ./project
& $cli report-issue inspect ./project $issueId
& $cli report-issue regenerate ./project $issueId ./new-output
& $cli report-issue export ./project ./complete-issued-project.zip
& $cli report-issue inspect-package ./complete-issued-project.zip
& $cli report-issue replay ./complete-issued-project.zip $issueId
```

Regeneration checks the frozen supported renderer/template/font identity and every deterministic output hash. If exact regeneration is unsupported, existing issued bytes remain readable and are not replaced. Replay runs only the explicitly selected issue's pair through the trusted compiled adapter; package commands are never executed.

The finite synthetic acceptance procedure is [declared separately](v0.7-issue-protocol.md), with reproducible orchestration in `scripts/verify-study-issues.ps1`. Full native workflow, final-source tests/package/CI, opening timing, cold regeneration and changed-page review remain individually tracked. Success in the synthetic procedure cannot establish private geometry intake or physical validation.
