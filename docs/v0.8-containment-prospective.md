# Prospective OpenSKP containment decision

2026-10-18. Source review for the separately authorized CT1 investigation in `docs/v0.8-report-design-continuation.md`. This is a source-only development record, not a parser test, native containment observation, compatibility claim or application dependency decision. Baseline source is `6d774d72be30f6695c1d8f588903b66de3f3622f`.

**Decision: stop before consuming CT1.** The current candidate does not establish maximum allocation requests and aggregate intermediate expansion across its parser, metadata and serializer closure. Consequently no numerical internal Job guard can yet be justified against the unchanged strict 1 GiB raw aggregate committed-memory ceiling. A few successful synthetic allocations would not close those source gaps. This is an engineering prerequisite, not a claim that a future bounded implementation is impossible, nor evidence that any particular SKP is corrupt or unrecoverable.

CT1 usage is **0/4 functional and 0/2 termination cases**. The existing fixed conversion matrix, repeats and private probe remain unspent. No worker build, fixture parsing, private-source access, SketchUp operation, renderer or engine execution occurred for this decision. Independent reporting and visual-design work can continue.

## Retained failure and measurement contract

The original 384 MiB experiment remains failed: raw `PeakJobMemoryUsed` reached **438,923,264 bytes** against **402,653,184 bytes**. The instrumented discriminator accepted a 256 MiB allocation, rejected a subsequent 160 MiB request with error 1455, and observed the requested region still reserved. Retained native private commitment stayed at 269,774,848 bytes; raw peak increased from 271,151,104 to 438,923,264 bytes. Those observations do not exclude a transient charge. Do not subtract the rejected request or substitute the post-request private value for the raw peak. The preserved record is `docs/evidence/v0.8/committed-accounting-checkpoint.json`, SHA-256 `f393ebbe6c6b7d9686f67a4a98bc6a746981c80d0cd69bf5c3672996b5fef49f`; its underlying observation receipt is `d8f219d1bffa5acc7f397abec2cac1b048f635ebb3d1f38102ab0044bf5e98b9`.

Microsoft documents that `JOB_OBJECT_LIMIT_JOB_MEMORY` rejects a commit that would exceed the Job-wide committed-memory limit. That is a retained-commit enforcement property; the cited API documentation does not provide a numeric bound on how a rejected request affects the reported raw high-water value. The historical observation prevents assuming the two are interchangeable. [Job limit flags](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information).

The kernel continuously tracks the extended Job peak fields. A held-Job query is therefore required before launch and after termination as well as during polling; a working-set maximum or a sum of independently timed process peaks is not an equivalent measurement. The documentation does not establish a general `raw peak <= configured limit + largest request` theorem. [Extended Job information](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information).

| Observation | What it establishes | What it does not establish |
|---|---|---|
| Held Job flags, memory/process limits and atomic launch | Configuration of the exact owned kernel Job, before child code starts | Geometry admission or correctness; arbitrary-library allocation bounds |
| Raw Job peak, retained without adjustment | Kernel-reported aggregate high-water observation for that Job | Why a denied request changed accounting; permission to ignore an exceedance |
| Held member `PrivateUsage` samples | Current private commit at those sample times | Absence of an unsampled transient, or an aggregate simultaneous peak |
| `PeakPagefileUsage` per member | That process's lifetime private-commit peak | Simultaneous total across descendants |
| Working set | Resident pages at an instant | Committed-memory containment |
| Denied allocation plus reserved region | That call failed and the later inspected region remained reserved | Proof that no transient charge occurred |
| Owned Job empty plus held member handles signaled | Observed termination of the owned tree | Termination of unrelated processes, which must never be requested |

The process-private fields and working-set fields have distinct definitions. Reservation and commitment also differ; reserved address space alone consumes no committed backing. [Process memory counters](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex), [VirtualAlloc](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualalloc).

## Allocation and expansion findings

These are source-derived findings, not executed malicious-file results. Some existing limits correctly precede their immediate allocations; they do not compose into a demonstrated peak bound automatically.

| Path | Existing admission | Remaining bound or ordering gap |
|---|---|---|
| Owned `read_source` | Positive source length <=128 MiB before `ByteBuffer(size)` | Final original-byte fence reads a second whole source while geometry/output are retained. Its extra request is <=128 MiB, but it contributes to simultaneous lifetime storage. |
| ZIP setup | Source itself <=128 MiB; miniz checks central-directory extent against archive | The owned 5,000-entry check executes **after** `mz_zip_reader_init_mem`. miniz has already allocated central-directory bytes and two offset arrays. Source extent bounds directory bytes to <=128 MiB, and its 46-byte minimum central-directory entry implies at most floor(128 MiB/46) entries before the later 5,000 check; each offset array is then <12 MiB. These finite bounds are not the intended pre-admission 5,000-entry limit. |
| ZIP extraction | Patched 64 MiB per declared entry, 256 MiB total declared/extracted bytes, checked before the output buffer | This bounds extracted byte buffers, not parsed node/maps/string copies or serializer intermediates. miniz allocation callbacks are not supplied with a shared byte budget. |
| Legacy typed arrays | Upstream per-array count <=100,000; patched recursive depth <=64 | `items.reserve(n)` precedes proof of enough remaining typed values, and does not debit a shared allocated-byte budget. Nested arrays can keep many such reservations live. The bound is not an arbitrary uint32 count; actual `sizeof(ParsedAttribute)`, container capacities and runtime allocation overhead require the selected build, not a guessed byte size. |
| TLV and dictionaries | Patched recursive depth and record count; checked payload ranges | Parsed payloads, flat records, dictionaries and textual views can coexist. Modern dictionary span traversal has depth checks but no shared byte accounting across its output strings/maps. Entity count is not a byte limit. |
| Triangulation and instance expansion | Before scene building, owned traversal checks 50,000 placed instances and a conservative one-million expanded-triangle bound | Upstream scene storage and material variants still allocate their own vectors/maps. A triangle count alone does not bound names, dictionaries, retained raw data and all simultaneous temporary buffers. |
| GLB binary preallocation | Subsequent append operations check the patched 64 MiB limit | `make_model` first sums primitive buffer sizes and calls `binary.reserve(total_bytes)` before those checks. The preallocation needs checked multiplication/addition and cap admission before reserve. |
| GLB JSON/stream | Serialized GLB length is checked against 64 MiB | TinyGLTF builds JSON and writes an `ostringstream`; `stream.str()` makes a further string before the cap is tested, then `ByteBuffer` copies it again. The final size limit is not a pre-allocation serializer limit. |
| Owned metadata and log JSON | Final metadata <=4 MiB and encoded log total <=1 MiB | `metadata.dump(2)` and per-message `.dump()` allocate encoded strings before their size checks. Metadata DOM assembly already duplicates names/inventories. Instance name checks do not bound every definition name; repeated occurrences can repeat source-derived text. JSON escaping can expand text. |
| Native runtime | Intended MSVC DLL runtime, BCrypt and Windows process services | Final imports, heap/string growth behavior, startup commitment and any runtime thread allocation have not been audited for this candidate binary. No maximum kernel commitment request across this closure has been established. |

The owned `patches.mjs` changes the stated limits but does not repair the ordering gaps above.

For example, the admissible byte limits `128 + 256 + 64 + 4 = 452 MiB` are **not** a working-memory bound: they concern different file/output contracts, omit intermediate duplicates and allocator overhead, and do not say which objects coexist. Similarly, choosing a 768 MiB guard and calling the remaining 256 MiB sufficient would require a proven bound on requests and accounting behavior which is absent. No proposed internal guard has been adopted or trial-tuned.

## Required held-Job observation and cleanup

The existing `NativeProcess.StartBounded` uses an atomic creation-time Job list, explicit inherited handles and a held Job handle. Any future worker collector must retain those safeguards and use the shared repaired observed-process path, exact Job membership, held PID/creation time and kernel image identity; never infer ownership from a process name. The worker's null-Job query sees the immediate containing Job only and cannot replace parent queries against its exact held Job. [QueryInformationJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-queryinformationjobobject).

Before a future case starts, query back x64 structure layout, `JOB_MEMORY`, `KILL_ON_JOB_CLOSE`, active-process bound and absence of breakaway flags. During and after the case record raw peak and all observed descendants, then require zero active Job members and signaled retained member handles within a declared cleanup deadline. Ordinary `CreateProcess` descendants inherit Job membership; nested Job accounting contributes to the parent. Completion-port notifications alone are not sufficient because most Job messages are not guaranteed. [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), [Nested Jobs](https://learn.microsoft.com/en-us/windows/win32/procthread/nested-jobs).

Parent cancellation/deadline must terminate only the owned Job and drain bounded stdout/stderr. A successful termination API return is not the final empty-tree observation. The owned parent retains its handle long enough to query final accounting. No receipt may call unresolved identity, overflow, missing EOF or failed cleanup a successful conversion. [TerminateJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-terminatejobobject).

## Smallest remedy and prospective gate

The next engineering work is a bounded source repair, not another unchanged memory experiment:

1. Move ZIP directory/count and GLB reserve admission ahead of the relevant allocations, with checked arithmetic. Bound legacy/modern dictionary aggregate growth before allocation rather than relying only on depth/entity caps.
2. Give metadata/log/GLB serialization a byte-counting bounded sink and account for DOM/string/stream duplication before growth. Inventory every retained phase and limit actual requested allocation sizes across OpenSKP, miniz, TinyGLTF/JSON and the selected native runtime; an output file cap alone is insufficient.
3. Audit the built closure and its maximum commitment requests, then choose one justified fixed internal guard below 1 GiB with the assumptions explicitly identified. Retain raw peak unadjusted. Source tests may verify the bound without running any SKP; worker compatibility remains a separate gate.
4. Only after that evidence exists, declare the at-most-four functional and two termination cases with exact bytes, requests, descendant counts, handshake states, positive controls, expected rejection class, per-case ceilings and cleanup deadlines. Every case runs once; at most 120 seconds per tree and 15 minutes total. A passed memory case cannot substitute for parser rejection classification or the geometric oracle.

No case-specific numerical guard or hypothetical output is frozen here because the prerequisite needed to justify it is missing. The authorized CT1 allowance is preserved, not silently weakened or spent on a test incapable of qualifying the actual candidate. The old 384 MiB failure remains failed even if a future different bounded implementation passes. A request to accept weaker accounting or raise limits would require separate authorization; this decision proposes neither.

Status: **verified source findings and primary-document review; containment unqualified; worker build/matrix/app adoption/private probe gated and unexecuted.** Independently authored legacy/modern fixtures already exist and remain unparsed. No new fixture acquisition or user authentication is required. The blocker is the missing bounded allocation/serialization closure and its native evidence, not a missing private export and not a proven private-file defect.
