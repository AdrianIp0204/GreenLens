# v0.8 reviewed documentation contracts

This supplement changes derived documentation, not thermal physics, run identities, scientific qualification or archive limits. The [v0.8 specification](v0.8-spec.md) defines acceptance; [v0.7 contracts](v0.7-contracts.md) remain authoritative for retained v1 history and issues. A structurally valid JSON object does not establish evidence integrity or complete provenance.

## Explicit version dispatch

New accepted documentation uses `greenlens.architectural-scope.v2`, `greenlens.scope-revision.v2`, `greenlens.scope-carry-forward.v2` and `greenlens.input-provenance-checklist.v2`. The optional project history container remains `greenlens.scope-history.v1`; it may retain both recognized revision versions. Reading a v1 project creates no revision and rewrites no member. Explicit adoption preserves an existing v1 scope and its exact snapshots before later v2 acceptance. Historical activation changes only the active pointer and compatibility projection.

Rust retains the v1 checklist, proposal, decision and parent-verification algorithms. V1 plans omit `candidate_scope`; their serialized bytes and identity prefix remain unchanged. A v2 child may have a v1 parent, but never upgrades that parent in place. V2 scope, checklist and revision versions must agree. Unknown versions reject.

Scope content hashes use `(scope.schema_version, scope)`. Revision and plan hashes use the recognized version and complete content with their own digest field empty. This preserves the original v1 tuple while giving changed semantics distinct identities. The global canonical JSON algorithm is unchanged. The existing exact scalar integral-float restoration at the typed revision transport boundary also remains: it does not normalize arbitrary source values or relax historical byte verification.

Report content and product envelopes retain their recognized v1 outer schemas; they embed the exact selected recognized scope revision. Renderer/template identity separately distinguishes changed output semantics. Do not infer a renderer or scientific status from the scope version. Old issued products, their source snapshots, and their hashes remain immutable.

## Typed field provenance

An assumption still retains its own source value, units, citation, rationale and affected scope. The checklist separately shows the actual analytical value. New links are:

```json
{ "kind": "study_field", "design_id": "B" }
{ "kind": "calendar_field", "design_id": "B" }
```

`field` is an exact JSON pointer into that design's retained typed `EnergyStudy` or `EnergyCalendar`. Examples are `/weather/original_sha256`, `/weather/normalized_sha256` and `/zone_timesteps_per_hour` for a study, and `/start_weekday`, `/utc_offset_minutes` or `/holidays/0/month` for a calendar. The pointer must resolve to an existing scalar. An absent design, unassigned study, nonexistent array index, aggregate object/array, `/schema_version` or `/calendar/...` study alias is rejected. A serialization-version string is not an applied scientific field. Calendar fields have their own explicit namespace. Hash declarations bind the actual selected weather identity; a source name alone cannot establish equivalence.

COP changes therefore retain unchanged typed weather/calendar declarations while changed COP declarations require review. A genuine weather/calendar field change affects its declaration, not an inferred whole-design substitute. Geometry/source revision changes still trigger stricter mapping, reconciliation and view review. Names never establish correspondence.

The legacy `{ "kind": "study" }` free-text link keeps its historical behavior in v1. On a v2 carry-forward it becomes explicitly missing/unresolved until the author chooses a supported typed field; text that resembles a pointer is not silently reinterpreted. V2 accepts that legacy row only with `missing` status and absent value. An empty register still produces unreviewed checklist fields. Missing documentation remains a disclosure, not a new prohibition on otherwise preflight-valid Unassessed execution.

## Editable candidate and atomic acceptance

A v2 review contains immutable `proposed_scope` and a separate complete `candidate_scope`. The editor reuses the existing mapping, assumption, reconciliation and view forms. Changes remain draft values until the user requests **Review edited candidate in Rust**. Rust recomputes the plan from the exact parent, current reference and model/study/calendar snapshots, plus that complete candidate. Review rows preserve before/after values and indicate additions, deletions, changed or unresolved records. Required rows need unique explicit decisions. Scope metadata review includes the exact set of design-model bindings; changing that set cannot hide behind unchanged individual mapping rows.

Acceptance supplies that plan digest, unchanged complete candidate and decisions. Rust recomputes both context and plan; a stale digest, invalid target, altered candidate, unknown decision or missing rationale fails atomically. No intermediate unresolved revision is necessary to correct a COP declaration. Failure/cancellation preserves the candidate draft and accepted history. Decisions may carry forward across a refreshed preview only when the complete corresponding review row is unchanged; a changed row requires renewed review.

Review rationales are limited to **2,048 UTF-8 bytes**, consistently in Rust and the editor. Byte-aware feedback counts multibyte text. Over-limit or invalid values remain in the draft and cannot create an accepted history entry. JSON Schema's character-length annotation alone does not enforce this byte rule; Rust is authoritative.

The ordinary per-document/design draft guards, one-writer conflict check, accepted transaction/undo rules and append-only history preservation remain. Review editing does not modify scientific inputs, replace a different live mapping, or silently rewrite the other design.

## Shared CLI

The no-candidate command still produces the mechanical proposal and initial candidate. Editing requires an explicit fresh review:

```powershell
greenlens reference scope-review .\study --parent <retained-revision-sha256>
greenlens reference scope-review .\study --parent <retained-revision-sha256> --candidate .\edited-scope.json
greenlens reference scope-accept .\study --parent <retained-revision-sha256> --plan <fresh-plan-sha256> --scope .\edited-scope.json --decisions .\review-decisions.json
```

The candidate file is bounded inert JSON, never a command recipe. CLI and desktop call the same Rust services. A preview performs no save; acceptance saves only the completely validated transaction using the verified expected project revision. Historical v1 inspection and recognized acceptance remain available.

## Bounds and wire schemas

Unchanged limits include 64 scope revisions, 32 issues, eight reference revisions, a 16 MiB pretty-printed project manifest when it contains scope history, 32 MiB per core revision, 16 MiB per carry-forward plan, 65,536 checklist/review rows, and the existing scope-specific item/string limits. Complete portable exports remain bounded to 5,000 entries, 64 MiB per entry and 256 MiB uncompressed. Maxima are admission bounds, not a guarantee that every combination fits; rejection preserves history instead of pruning it.

The new descriptive schemas are [scope](../schemas/architectural-scope-v0.8.schema.json), [revision](../schemas/scope-revision-v0.8.schema.json), [review plan](../schemas/scope-carry-forward-v0.8.schema.json) and [checklist](../schemas/input-provenance-v0.8.schema.json). Old schema files are unchanged. Rust additionally verifies exact snapshot membership, typed-pointer existence, canonical identities, row/decision coverage, actual reference bytes and atomic publication. No schema grants permission to execute imported commands, make a scientific qualification claim, or discard required assets.

## Delivery and capacity contracts

`greenlens.report-product-delivery.v1` distinguishes verified retained bytes, copy preparation, requested/failed/not-requested Windows handoff, and unobserved external viewer display. It never reports that a PDF opened merely because Windows accepted a handoff. Save Copy requires a new filename; PDF/PNG bytes are written to a bounded sibling temporary, re-hashed through the same open handle, and promoted without replacement after a final cancellation fence. Cancellation before promotion publishes no final file. Cancellation after successful publication retains a prepared-copy receipt and suppresses a pending handoff. Existing cache/viewer bytes are preserved. Inline preview is separately bounded to 8 MiB; it does not change issued PDF bytes.

`greenlens.project-capacity.v1` reports actual manifest-bound file sizes, known incremental lower bounds, optional explicitly uncertain estimates, effective limits and reasons. It is not an integrity verdict and does not authorize reuse of unchecked content. Actual-byte verification still occurs at evidence boundaries. Candidate publication checks the complete retained project and effective manifest limits; export separately admits its final archive including its envelope. Neither service silently prunes history or promises that an unknown report/import output will fit. Failed publication leaves completed pending evidence available for its existing recovery flow.

The [acceptance ledger](v0.8-acceptance.md) separates focused source checks from pending final-source, report-rendering, installed and CI evidence. Versioned contract implementation alone does not establish delivery acceptance.
