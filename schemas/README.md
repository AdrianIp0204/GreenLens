# Serialized contracts

`model-v0.1.schema.json` documents editable model input. `project-v0.1.schema.json` documents the portable `project.json` manifest. `run-v0.1.schema.json` documents completed `results.json` records. `checksums-v0.1.schema.json` documents per-run and exported-package integrity manifests. Register schemas by their `urn:greenlens:...` identifiers when using a generic JSON Schema validator; the project and run schemas reference the model schema by that identifier.

These schemas describe structure. The shared Rust application service remains authoritative for dependent constraints, geometry, exact A/B alternative identities, stable sensor definitions, run references, scientific fingerprints, checksum coverage, process success and raw-to-processed result consistency. Schema validation alone does not establish a completed run or authorize replay.

`results.json` stores a `greenlens_runner::RunRecord`: immutable model input, authoritative validated geometry/sensors and fingerprints, ordered `lux` values, min/mean/max/count statistics, and provenance. Its provenance carries `schema_version: "0.1.0"`, state `completed`, units `lx`, application/adapter/engine identities, frozen numerical profile, UTC timestamps, successful process records and separate comparison/run fingerprints. `results.csv` is a table fallback for the same ordered sensor values. The stable Rust types and `docs/model-contract.md` specify those calculated fields; they are always regenerated or validated from inputs on load.

Saved and exported paths are relative to their project/run root. No schema grants permission to execute package-supplied commands. `replay` uses the installed pinned adapter and engine, validates evidence and rebuilds disposable octrees.

The thermal model, energy study and immutable energy report remain under their v0.4 schemas. v0.5 adds optional, independently versioned workbench state and supplementary comparison, report and sensitivity contracts described in [workbench contracts](../docs/v0.5-contracts.md). Absence of these extensions is valid for historical projects. Their authoritative Rust readers enforce bounds, exact identities and sidecar checksums; a descriptive schema is not a substitute. Imported sensitivity receipts never authorize an engine launch or a favorable re-selection of runs. The strict historical weather profile is unchanged; the separately identified dry-envelope policy does not relabel old weather evidence.

The climate extension is documented by `project-v0.3.schema.json`, `study-v0.3.schema.json` and `timeseries-v0.3.schema.json`. Its outer run schema remains `greenlens.climate-run.v0.3`; a distinct engine recipe version binds numerical method, complete profile, generated inputs and recognized processes. Recipe versions 2–4 remain historical. Version 4 retains scaled coefficient receiver and repeated-primary input files; provisional version 5 instead retains compact paired-generator receipts documented by `primary-streams-v1.schema.json`. Neither changes the unique sensor/time axis. Rust requires the exact known method/schema/adapter/profile tuple, regenerated inputs and cross-record receipt/resource equality, not merely structurally valid JSON. The generator schema lists all supported generator counts; production profile allowlisting remains narrower and authoritative. See [climate contracts](../docs/v0.3-contracts.md) for identity and compatibility rules. Historical evidence bytes are never migrated in place.
